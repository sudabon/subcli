# Design

## Context

Phase 1 の `policy` と Phase 2 の `runner` / `event` / `render` / `claude`・`codex` アダプタを基盤として、複数プロバイダを扱う `compare` と `chain` を構築する。モチベーションは `proposal.md`、要求仕様は `specs/multi-provider-workflows/spec.md` を参照。

## Goals / Non-Goals

**Goals:**
- `compare` / `chain` ともに全参加者の `policy.Check` を事前検証し、1 件でも NG なら全体を起動前にブロックする。
- `compare` でプロバイダごとの `max_concurrency` を守るセマフォ制御と、横並び TTY / JSONL 表示を実現する。
- `chain` で `text/template` による `{{.Prev}}` 展開と最大 3 段の固定直列実行を実現する。

**Non-Goals:**
- 動的な分岐・条件付きループ・自動リトライループ・自律マルチエージェント閉ループ。
- `agy`（`auth=subscription`）の参加許可（Phase 4 で `auth=api_key` のみ参加可能になる）。

## Decisions

### 1. 事前ポリシー検証のフェーズ分離
- **決定**: `compare` は `OpCompare`、`chain` は `OpChain` で、指定された全プロバイダ（重複含む）に対して事前ループで `policy.Check` を実行する。1 つでも `!Allow` があれば即座にエラー返却する。
- **理由**: `spce.md` §7.2「`compare` / `chain` の参加者に agy(subscription) が含まれていたら、実行前に全体を拒否する」を厳密に満たし、途中課金や不要な子プロセス起動を防ぐ。

### 2. `compare` の並列実行と `max_concurrency` 制御
- **決定**: プロバイダ ID ごとに容量 `max_concurrency` のチャネルセマフォを持ち、各実行ゴルーチンが取得→`runner.Run`→解放を行う。イベントは共通チャネル（`provider` タグと実行インデックス付き）へ集約し、`--json` 時は到着順に JSONL 出力、TTY 時は端末幅に応じた横並びレイアウト（完了後にカラム整形、または幅不足時はプロバイダ別セクション表示へフォールバック）で描画する。
- **理由**: 同時実行数制御が単体テストで検証しやすく、偽 CLI を使って最大同時起動数を正確にアサートできる。

### 3. `chain` のテンプレート展開とステップ数制約
- **決定**: `--steps` をカンマ分割し、`len(steps) < 2 || len(steps) > 3` なら実行前エラーとする。`--then` は 1 つ指定（2 段目・3 段目で共通利用）またはステップ数-1 個の複数指定を許可し、Go 標準の `text/template` で `struct{ Prev string }` を展開する。各段の `Prev` には直前段の `event.Text` 連結結果を用いる。
- **理由**: 単純明快かつ完全に非循環であり、任意のコード実行やループ制御構造をコマンド設計から排除できる。
- **補足**: `--then` に複数指定がない場合でも 3 段構成で動くよう、`--then` は `StringArray` フラグとして 1 回（全後続段で再利用）または `len(steps)-1` 回の指定を受け付ける。

## Risks / Trade-offs

- [TTY 横並び表示が狭いターミナル幅で崩れる] → 端末幅が閾値（例: 100 桁）未満の場合はプロバイダ見出し付きの縦並びブロック表示へ安全にフォールバックし、可読性を維持する。
- [前段プロバイダの最終テキストが空だった場合] → 空のまま次段へ流すか警告・エラーにするかを明確化し、前段がエラー終了した場合は即中断、正常終了かつ出力空の場合は明確なエラーで停止して無意味な次段呼び出しを防ぐ。
- [`compare` で一部プロバイダが失敗した場合の終了コード] → 他のプロバイダの完了を待って結果とエラーをすべて表示したうえで、1 つ以上失敗があれば非ゼロ終了コードを返す。
